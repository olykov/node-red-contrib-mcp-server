# ТЗ: виправлення @olykov/node-red-mcp-server

16 жовт. 2026 р. · @Yehor

ТЗ закриває всі 20 знахідок з `Document` трьома релізами: 3.4 знімає блокери продового встановлення, 3.5 доводить пакет до публікації в npm, 4.0 змінює контракт нод. Кожна вимога має ID, критерій приймання і спосіб перевірки; ці ID стануть основою `check-req-ids`, коли ТЗ ляже в репозиторій як `docs/spec.md`.

## 1. Мета і межі

Після 3.4 пакет можна ставити в продовий Node-RED, після 3.5 публікувати в npm і Flow Library, і жоден реліз не втрачає гарантій безпеки, які пакет дає зараз (розділ 6).

Входить. HTTP-шар MCP і OAuth-роутів, реєстр інструментів, тести і CI, мережеві налаштування `mcp-runtime`, `get_flow`, відповідність протоколу MCP, сховище авторизації, пакування і публікація, контракт нод 4.0 і міграція на нього.

Поза обсягом. Нові можливості MCP (resources, prompts, sampling, elicitation), нові провайдери ідентичності, зміна моделі токенів і сесій, будь-які інструменти запису через admin API.

Позначення. Перевірка `unit` іде на моку, `integration` на справжньому Node-RED 5.x через `node-red-node-test-helper` або запущений процес, `CI` це перевірки пакета і пайплайна, `review` це перевірка читанням коду. У дужках після ID стоїть знахідка з ревʼю, яку вимога закриває. Значення за замовчуванням у вимогах це пропозиція ТЗ: інше значення не змінює суті вимоги.

## 5. Вимоги 4.0

4.0 приводить пакет до ідіом Node-RED: виклик інструмента проходить флоу в один бік, спільні ресурси належать конфіг-нодам, типи мають унікальний префікс. Реліз несумісний з 3.x, тому без міграції MCP-MIG-1 він не виходить. `<prefix>` нижче це префікс з відкритого питання 1.

| Тип 3.x | Тип 4.0 | Роль |
| --- | --- | --- |
| `mcp-runtime` | `<prefix>-runtime` | конфіг-нода: слухач порту, реєстр інструментів, admin-налаштування |
| `mcp-flow-server` | `<prefix>-endpoint` | конфіг-нода: шлях, MCP-імʼя, групи, auth, ліміти |
| `mcp-tool-registry` | `<prefix>-tool` | початок флоу інструмента |
|  | `<prefix>-tool-response` | кінець флоу, відповідь клієнту |
| `mcp-server-metrics` | `<prefix>-metrics` | джерело телеметрії |
| `mcp-auth` | `<prefix>-auth` | конфіг-нода провайдера |
| `mcp-redis` | `<prefix>-auth-storage` | конфіг-нода сховища |

## 7. Definition of Done

Реліз виходить, лише коли виконано всі пункти його блоку; блоки накопичуються, тож 3.5 включає DoD 3.4, а 4.0 обидва.

### 3.4

- Кожна вимога розділу 3 має тест або позначку review з посиланням на PR
- CI зелений: lint, unit, integration, smoke з тарбола, матриця MCP-TEST-3
- Покриття не нижче поточних порогів 90% рядків, 80% гілок, 85% функцій
- Тести інваріантів розділу 6 зелені без зміни очікувань
- CHANGELOG і «Upgrading to 3.4»
- Реліз-кандидат стоїть на копії продового інстансу з реальним провайдером; Claude Code і Codex проходять вхід, `tools/list` і `tools/call`

### 3.5

- Кожна вимога розділу 4 має тест або позначку review
- ТЗ лежить у репозиторії як `docs/spec.md`, а CI перевіряє, що кожен ID має тест чи позначку review
- Перша публікація йде через MCP-PKG-2; версію, provenance і вміст тарбола звірено після публікації
- Пакет подано у Flow Library; картка показує README, версію Node-RED, приклад і команду встановлення

### 4.0

- Кожна вимога розділу 5 має тест або позначку review
- MCP-MIG-1 прогнано на копії реальних флоу; rollback на 3.5 перевірено
- Help, приклади і message catalogs описують лише нові типи

## 8. Відкриті питання

1. Префікс типів 4.0. Від нього залежать імена в розділі 5 і CLI міграції: префікс автора на кшталт `olykov-mcp-` чи нейтральний.
2. Цільова ревізія MCP для 4.0. Лишитися на 2025-11-25 чи перейти на [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog), де немає `initialize`, `server/discover` обовʼязковий, а результати мають `resultType`. Від цього залежить, що лишається анонімним, бо зараз анонімне лише рукостискання.
3. `bindHost` для наявних конфігурацій. Як у MCP-NET-2, усі інтерфейси з попередженням, чи обовʼязкове поле вже в 3.4 ціною ручного кроку при оновленні.
4. Валідатор для MCP-VAL-3. Нова залежність з режимом JSON Schema 2020-12 чи власна перевірка обмеженої підмножини.
5. Керування ендпоінтом під час роботи. Чи потрібна заміна командам start, stop і restart, які 4.0 прибирає.
6. HTTPS admin API з власним CA для MCP-ADM-3. Окреме поле для CA чи лише loopback HTTP.
7. Підтримка 3.5.x після 4.0. Скільки часу і які виправлення: лише безпека чи й помилки.

**Вирішено під час 3.4/3.5:** #3 — `bindHost` лишився опційним у 3.4/3.5: нові ноди отримують `127.0.0.1`, наявні без поля слухають усі інтерфейси з попередженням (MCP-NET-2). #4 — Ajv з режимом JSON Schema 2020-12 (MCP-VAL-3). #6 — окреме поле **CA** для admin HTTP-клієнта, а не лише loopback HTTP (MCP-ADM-3). Питання #1, #2, #5 і #7 лишаються відкритими для 4.0.
